Rancangan pada praktikum ini dapat dikategorikan sebagai Adapter Pattern karena terdapat sebuah program perantara yang menghubungkan sistem modern dengan sistem legacy. Sistem legacy yang digunakan pada praktikum ini adalah program C yang hanya dapat membaca dan menulis data pada file students_db.txt. Sistem tersebut tidak mempunyai kemampuan untuk menerima request HTTP atau memahami data dalam format XML. Karena itu, dibuatlah adapter_service.py sebagai Adapter yang berada di tengah-tengah kedua sistem tersebut. Adapter menerima request dari client menggunakan HTTP, kemudian mengolah data XML tersebut agar dapat dibaca atau disimpan ke dalam format yang digunakan oleh sistem legacy. Keuntungan dari penggunaan Adapter ini adalah sistem legacy tidak perlu diubah atau ditulis ulang agar bisa digunakan oleh aplikasi modern. Client dari luar cukup berkomunikasi dengan Adapter menggunakan HTTP dan XML, tanpa perlu mengetahui bagaimana sebenarnya data mahasiswa disimpan di dalam students_db.txt. Misalnya, ketika client mengirim data mahasiswa menggunakan POST, client cukup mengirim XML kepada Adapter. Setelah itu Adapter yang bertugas mengambil data dari XML dan menyimpannya ke file teks yang digunakan sistem legacy. Dengan cara ini, sistem lama tetap dapat digunakan, sedangkan aplikasi modern tetap bisa berkomunikasi menggunakan teknologi yang lebih umum seperti HTTP dan XML.
Pada praktikum ini, data mahasiswa sebenarnya cukup sederhana, yaitu NIM, nama, jurusan, dan status. Contohnya data aktual untuk mahasiswa dengan NIM 2415354001 adalah 2415354001, I Made Sujana, Teknologi Informasi, dan ACTIVE. Jika data tersebut hanya ditulis sebagai data biasa, ukurannya relatif kecil karena hanya berisi informasi yang memang dibutuhkan. Namun ketika data dikirim menggunakan XML, data tersebut harus dibungkus dengan berbagai tag seperti <StudentResponse>, <NIM>, <Nama>, <Jurusan>, dan <Status>. Tag-tag tersebut tidak berisi informasi mahasiswa tambahan, tetapi tetap membutuhkan ruang dalam data yang dikirim melalui jaringan. Hal inilah yang disebut overhead serialisasi XML. Untuk menghitungnya, pertama kita perlu menghitung jumlah byte dari data aktual saja, yaitu 2415354001, I Made Sujana, Teknologi Informasi, dan ACTIVE. Setelah itu kita menghitung jumlah byte dari seluruh respons XML yang diterima, termasuk semua tag pembungkus dan deklarasi XML jika terdapat pada respons. Selisih antara ukuran seluruh XML dengan ukuran data aktual menunjukkan berapa banyak tambahan data yang muncul akibat penggunaan format XML. Rumus yang digunakan adalah: overhead = (total byte XML - byte data aktual) / byte data aktual × 100%. Jadi, semakin banyak tag XML yang digunakan dibandingkan isi datanya, semakin besar pula overhead yang dihasilkan.Dalam praktikum ini, angka akhirnya sebaiknya dihitung berdasarkan hasil XML yang benar-benar muncul pada komputer saat menjalankan GET /students/2415354001, karena ukuran respons yang sebenarnya menjadi dasar perhitungan. Dengan begitu, hasil laporan sesuai dengan pengujian yang dilakukan, bukan hanya menggunakan angka perkiraan. Intinya, XML memang membuat data lebih terstruktur dan mudah dipahami oleh sistem yang berbeda, tetapi sebagai konsekuensinya ukuran data menjadi lebih besar karena adanya tag-tag XML.
Jika 500 permintaan POST dikirim secara bersamaan pada detik yang sama, maka semua permintaan tersebut akan mencoba memasukkan data ke file students_db.txt melalui Adapter. Masalahnya, sistem pada praktikum ini masih menggunakan file teks sederhana sebagai tempat penyimpanan data. File tersebut belum dirancang seperti database modern yang memiliki mekanisme khusus untuk menangani banyak proses penulisan secara bersamaan. Akibatnya, ketika banyak request datang dalam waktu yang sama, proses penulisan dapat menjadi tidak teratur dan berpotensi menyebabkan data tidak tersimpan dengan benar atau terjadi masalah pada integritas isi file. Semakin banyak request yang datang bersamaan, semakin besar pula beban operasi input/output pada file tersebut Masalah tersebut dapat menjadi semakin serius jika jumlah request terus bertambah. Adapter harus menangani request satu per satu, membaca data XML, kemudian membuka dan menulis ke file. Jika banyak request datang bersamaan, sistem tidak memiliki antrean khusus yang mengatur urutan pekerjaan tersebut. Karena itu, pada sistem yang lebih besar dapat digunakan Message Broker sebagai perantara. Request yang masuk tidak langsung semuanya menulis ke file, tetapi terlebih dahulu dimasukkan ke dalam antrean pesan. Setelah itu, proses worker atau Adapter dapat mengambil pesan dari antrean secara teratur dan memprosesnya satu per satu. Dengan cara ini, beban penulisan dapat lebih terkontrol dan kemungkinan terjadinya konflik saat banyak request mengakses file secara bersamaan dapat dikurangi. Konsep ini menjadi penting ketika sistem berkembang dan jumlah request jauh lebih besar dibandingkan contoh praktikum yang hanya menggunakan beberapa data mahasiswa
